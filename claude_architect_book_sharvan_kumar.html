The Agentic Loop

Every Claude agent runs on the same fundamental loop. Your code sends messages, Claude reasons and either calls a tool or finishes. You react to stop_reason.

stop_reasonMeaningYour code does
"tool_use"Claude wants to call a tool before finishingExecute tool → append result → send again
"end_turn"Claude is done — final answer readyRead response.content[0].text → exit loop
Complete Agentic Loop — Production Pattern
import anthropic, json

client = anthropic.Anthropic()

def run_agent(user_message: str, tools: list, system: str = ""):
    messages = [{"role": "user", "content": user_message}]
    iteration = 0
    MAX_ITER = 20  # safety cap — NOT the primary stopping mechanism

    while iteration < MAX_ITER:
        iteration += 1

        response = client.messages.create(
            model="claude-sonnet-4-20250514",
            max_tokens=1000,
            system=system,
            tools=tools,
            messages=messages
        )

        # ✅ CORRECT — stop_reason drives loop control
        if response.stop_reason == "end_turn":
            for block in response.content:
                if hasattr(block, "text"):
                    return block.text
            break

        elif response.stop_reason == "tool_use":
            # Append Claude's full response (with tool calls) to history
            messages.append({
                "role": "assistant",
                "content": response.content
            })

            # Execute every tool Claude requested
            tool_results = []
            for block in response.content:
                if block.type == "tool_use":
                    result = execute_tool(block.name, block.input)
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": json.dumps(result)
                    })

            # Append all results and loop again
            messages.append({"role": "user", "content": tool_results})
⚠ Exam Trap — Loop Anti-Patterns (These Are Wrong)

❌ Checking if response text contains "I have completed" or similar
❌ Using an iteration cap as the PRIMARY stopping mechanism
❌ Checking for assistant text content as a completion indicator
❌ Parsing natural language signals to determine loop termination

✅ One correct answer: stop when stop_reason == "end_turn"

Multi-Agent Orchestration

Hub-and-spoke architecture: the coordinator manages all communication, error handling, and routing. Subagents are specialists with isolated context.

The most tested fact about subagents: They have ZERO automatic context inheritance. They cannot see what the coordinator knows. You must explicitly inject everything they need directly into their prompt.

# ✅ CORRECT — explicit context injection to subagent
web_search_results = "... [findings from web search agent] ..."
doc_analysis_results = "... [findings from document analysis agent] ..."

synthesis_prompt = f"""
You are a synthesis agent. Combine these research findings into a report.

WEB SEARCH FINDINGS:
{web_search_results}

DOCUMENT ANALYSIS FINDINGS:
{doc_analysis_results}

Synthesize into a comprehensive report with source attribution.
"""
# The subagent now has everything it needs — explicitly provided

⚠ Exam Trap — Task Tool Configuration

For a coordinator to spawn subagents, allowedTools must explicitly include "Task". Without this, the coordinator cannot invoke subagents regardless of what its system prompt says.

# PostToolUse hook — normalize heterogeneous tool outputs
def post_tool_use_hook(tool_name: str, tool_result: dict) -> dict:
    """Normalize formats before Claude processes the result"""

    if tool_name == "get_order":
        # Convert Unix timestamp to readable format
        if "created_at_unix" in tool_result:
            tool_result["created_at"] = datetime.fromtimestamp(
                tool_result["created_at_unix"]
            ).isoformat()

        # Convert numeric status codes to labels
        status_map = {1: "placed", 3: "shipped", 7: "delivered", 9: "returned"}
        tool_result["status"] = status_map.get(tool_result.get("status_code"), "unknown")

    return tool_result

# Pre-tool interception hook — enforce business rules
def pre_tool_hook(tool_name: str, tool_input: dict) -> dict | None:
    """Return None to block, return modified input to allow"""

    if tool_name == "process_refund":
        amount = tool_input.get("amount", 0)
        if amount > 10000:
            # Block and redirect to escalation
            return None  # signals: do not execute this tool call
    return tool_input  # allow the tool to proceed
✓ Hooks vs Prompt Instructions

Hooks give deterministic guarantees. Prompt instructions give probabilistic compliance.

When a business rule has financial or compliance consequences (identity verification before refunds, blocking operations above a threshold), use hooks — not instructions. Prompt instructions have a non-zero failure rate even when written perfectly.

Domain 1 — Practice Questions (10)

Q1. Your agent skips get_customer and calls process_refund directly in 8% of cases, causing financial errors. What is the most effective fix?
  • A) Add a programmatic prerequisite blocking process_refund until get_customer returns a verified customer ID
  • B) Enhance the system prompt: "always call get_customer before any financial operations"
  • C) Add 5-8 few-shot examples showing correct tool ordering
  • D) Implement a classifier that restricts available tools based on conversation stage
A — Programmatic enforcement is deterministic. Options B and C are probabilistic — prompt instructions have a non-zero failure rate. At 8% failure rate on financial operations, prompt-based approaches are insufficient.
Q2. A coordinator emits two Task tool calls in a single response. What is the execution pattern?
  • A) The second Task waits for the first to complete before starting
  • B) Both subagents execute in parallel simultaneously
  • C) The coordinator selects whichever Task is most relevant
  • D) The second Task is ignored — only one Task per turn is supported
B — Multiple Task tool calls in one coordinator response = parallel execution. This is how you achieve concurrent subagent processing rather than sequential.
Q3. Your research system covers only technology topics when asked to research "global supply chain disruptions." Each subagent completed successfully. Root cause?
  • A) The synthesis agent filtered out non-technology findings
  • B) The coordinator's task decomposition was too narrow — only assigned technology subtasks
  • C) The web search agent used technology-biased search queries
  • D) The document analysis agent used overly restrictive relevance criteria
B — Subagents executed their assigned scope correctly. The coordinator decomposed "supply chain disruptions" into only technology subtasks, missing economics, geopolitics, and logistics. The problem is what they were assigned, not how they performed.
Q4. Your agentic loop checks: "if 'task complete' appears in Claude's response, exit loop." What is wrong with this approach?
  • A) Claude may not always include those exact words
  • B) It's a natural language signal anti-pattern — loop termination must be driven by stop_reason == "end_turn", not text content
  • C) Response parsing is too slow for production systems
  • D) Text content is not available when stop_reason is "tool_use"
B — Parsing natural language signals for loop termination is an explicit anti-pattern. The only reliable termination condition is stop_reason == "end_turn". Claude controls when it's done — your code should respect that signal.
Q5. A synthesis subagent needs findings from the web search and document analysis subagents. How does it receive this information?
  • A) Subagents automatically share a common memory space
  • B) The coordinator injects all findings explicitly into the synthesis subagent's prompt
  • C) The synthesis agent reads results directly from previous subagents' output files
  • D) The Agent SDK passes context between subagents automatically
B — Subagents have zero automatic context inheritance. The coordinator must explicitly inject all required findings into the synthesis subagent's prompt. Nothing is shared automatically.
Q6. Your PostToolUse hook normalizes Unix timestamps to ISO 8601 format. When does this hook fire?
  • A) Before the tool executes, so Claude sees normalized inputs
  • B) After the tool executes but before Claude processes the result
  • C) After Claude processes the result, as post-processing cleanup
  • D) When Claude decides which tool to call next
B — PostToolUse fires after tool execution but before Claude sees the result. This is the correct position to normalize data so Claude always receives consistent, well-formatted tool outputs.
Q7. When should you choose fork_session over --resume?
  • A) When the prior session's tool results are stale after code changes
  • B) When you want to explore two divergent approaches from a shared analysis baseline simultaneously
  • C) When the session name is not known
  • D) When the codebase is too large for a single session
B — fork_session creates independent branches from a shared baseline for divergent exploration. --resume continues the same session. For stale results, start a new session with an injected summary.
Q8. A refund of ₹15,000 needs manager approval. You add "never process refunds above ₹10,000 without escalation" to the system prompt. Is this sufficient?
  • A) Yes — explicit instructions in system prompts are always followed
  • B) No — prompt instructions have a non-zero failure rate; use a pre-tool interception hook for deterministic enforcement
  • C) Yes — but only if few-shot examples are also provided
  • D) No — system prompts cannot reference specific monetary amounts
B — For business rules with financial consequences, prompt instructions are insufficient. A pre-tool interception hook provides deterministic guarantees — it physically blocks the tool call if the threshold is exceeded.
Q9. What must allowedTools include for a coordinator to spawn subagents?
  • A) The names of all subagent types
  • B) "Task"
  • C) "SubAgent"
  • D) "Delegate"
B — "Task" is the specific mechanism for spawning subagents in the Claude Agent SDK. Without "Task" in allowedTools, the coordinator cannot invoke subagents regardless of other configuration.
Q10. After resuming a session, the agent references the state of a file that was refactored since the session ended. What should you do?
  • A) Always start a new session — resumed sessions can never account for code changes
  • B) Inform the agent about the specific file changes for targeted re-analysis rather than requiring full re-exploration
  • C) Use fork_session to create a branch with the updated files
  • D) The session automatically detects file changes and updates its understanding
B — When resuming after code changes, inform the agent about specific changed files for targeted re-analysis. This is more efficient than full re-exploration and more accurate than ignoring the changes.

Writing Effective Tool Descriptions

Tool descriptions are the routing table Claude uses for tool selection. Minimal descriptions cause misrouting. Good descriptions include: purpose, expected inputs, example queries, edge cases, and explicit boundaries.

# ❌ BAD — causes misrouting between similar tools
{"name": "analyze_content", "description": "Analyzes content"}
{"name": "analyze_document", "description": "Analyzes documents"}
# Near-identical descriptions = Claude picks randomly

# ✅ GOOD — clear differentiation with boundaries
{
    "name": "extract_web_results",
    "description": """Extracts structured data from web search HTML or JSON.
USE FOR: raw content fetched from a URL, news article, or web page.
INPUT: Raw HTML, JSON response, or plain text from a web source.
OUTPUT: Structured findings with source URLs, titles, key facts.
DO NOT USE FOR: PDF files, uploaded documents, database exports."""
},
{
    "name": "analyze_document",
    "description": """Analyzes uploaded documents — PDF, DOCX, structured text.
USE FOR: uploaded files — research papers, contracts, reports, specs.
INPUT: Document text content extracted from a file.
OUTPUT: Key claims, methodology, data points with page references.
DO NOT USE FOR: live web content, API responses, real-time data."""
}

def get_customer(customer_id: str) -> dict:
    try:
        result = api.fetch_customer(customer_id)
        return {"isError": False, **result}

    except TimeoutError:
        return {
            "isError": True,
            "errorCategory": "transient",
            "isRetryable": True,
            "description": "Customer API timed out. Retry is appropriate.",
            "attemptedQuery": f"GET /customers/{customer_id}"
        }
    except PolicyViolation as e:
        return {
            "isError": True,
            "errorCategory": "business",
            "isRetryable": False,
            "description": str(e),
            "customerMessage": "This account has a restriction. Contact our team.",
            "retriable": False
        }

Domain 2 — Practice Questions (10)

Q1. Two tools have nearly identical descriptions. What is the most likely observable symptom in production?
  • A) Both tools are called simultaneously for every request
  • B) The model rotates between them unpredictably for semantically similar requests
  • C) An error is thrown due to ambiguous tool selection
  • D) The model refuses to use either tool and returns text instead
B — Minimal or overlapping descriptions cause unreliable selection — the model lacks context to differentiate. The fix is enriching descriptions with clear purpose, input formats, example queries, and explicit "do not use for" boundaries.
Q2. Your MCP tool returns an empty array [] for a customer with no orders. Should this use isError: true?
  • A) Yes — no orders found is an error condition
  • B) No — empty result is a valid successful response; isError: true is for access failures
  • C) Yes — the coordinator needs to know no data was returned
  • D) It depends on whether the customer exists
B — An empty array is a successful query with no matches. isError: true signals access failures, timeouts, or policy violations — not valid empty results. Confusing the two prevents intelligent coordinator recovery.
Q3. A developer wants to test a new experimental MCP server without affecting teammates. Where should they configure it?
  • A) .mcp.json with an experimental: true flag
  • B) ~/.claude.json — user-scoped, not version controlled
  • C) A separate .mcp.experimental.json file
  • D) .claude/config.json with a personal section
B — ~/.claude.json is user-scoped and never version controlled, making it the correct location for personal or experimental servers that should not affect teammates.
Q4. Your synthesis agent keeps attempting web searches mid-synthesis instead of synthesizing. What is the root architectural cause?
  • A) The synthesis agent's system prompt is ambiguous about its role
  • B) The synthesis agent has access to web search tools outside its specialization
  • C) The coordinator is not passing sufficient context to the synthesis agent
  • D) The synthesis agent needs a stronger persona definition
B — When agents have tools outside their specialization, they misuse them. Remove web search tools from the synthesis agent. Provide only a scoped verify_fact tool for simple lookups. Complex verification routes through the coordinator.
Q5. tool_choice: "any" vs tool_choice: "auto" — what is the key difference?
  • A) "any" lets Claude pick any tool; "auto" forces a random tool
  • B) "any" guarantees Claude calls a tool (not text); "auto" may return conversational text instead
  • C) "any" uses all available tools; "auto" uses only the most relevant one
  • D) They are equivalent — both allow Claude to decide
B — "auto" allows Claude to respond with text instead of calling a tool. "any" guarantees a tool call but Claude chooses which. For guaranteed structured output, use forced selection: {"type": "tool", "name": "specific_tool"}.
Q6. A Jira MCP server exists in the community. When should you build a custom implementation instead?
  • A) Always — custom implementations give better control
  • B) Only for team-specific workflows not covered by the community server
  • C) When the team has more than 10 developers
  • D) When the Jira instance is self-hosted
B — Use existing community MCP servers for standard integrations. Reserve custom implementations for team-specific workflows not covered by community servers. This avoids unnecessary maintenance overhead.
Q7. An MCP tool returns "Operation failed" for all error types. What specific problem does this cause?
  • A) Claude cannot display the error to the user
  • B) The agent cannot distinguish transient failures (retry) from business violations (don't retry), leading to wasted retries or missed recovery opportunities
  • C) The isError flag requires a specific message format
  • D) Generic messages cause Claude to escalate all errors to humans
B — Without errorCategory and isRetryable, the agent cannot make intelligent recovery decisions. Should it retry? Reformulate? Escalate? Inform the customer? Generic errors make all these decisions impossible.
Q8. How do you prevent GitHub tokens from being committed to version control in .mcp.json?
  • A) Add .mcp.json to .gitignore
  • B) Use ${GITHUB_TOKEN} environment variable expansion in .mcp.json
  • C) Encrypt the token using a project-level key
  • D) Store tokens in ~/.claude.json instead
B — Environment variable expansion (${GITHUB_TOKEN}) lets you commit .mcp.json safely — the actual token value is read from the environment at runtime, never stored in the file.
Q9. Your agent has 18 tools and tool selection accuracy is 60%. What is the first fix to try?
  • A) Add detailed instructions to system prompt about when to use each tool
  • B) Add few-shot examples demonstrating correct tool selection
  • C) Reduce each agent's tool set to only those needed for its specific role (4-5 tools)
  • D) Switch to a larger model with better tool selection capability
C — Too many tools increases decision complexity and degrades selection reliability. Restricting to role-relevant tools (4-5) is the most impactful fix. Instructions and few-shot examples are secondary improvements after the tool count is right.
Q10. MCP resources vs MCP tools — what is the key difference in purpose?
  • A) Resources are faster to call; tools are more reliable
  • B) Resources expose content catalogs (data agents can browse); tools perform actions (functions agents call)
  • C) Resources are read-only; tools can write to backend systems
  • D) Resources are configured in .mcp.json; tools are defined in the API call
B — MCP resources expose content catalogs (issue summaries, documentation hierarchies, database schemas) to give agents visibility without exploratory tool calls. MCP tools are callable functions that perform actions.

⚠ Most Tested Trap in Domain 3

"A new team member is not getting the coding standards everyone else receives."

Root cause: Standards are in ~/.claude/CLAUDE.md — user level, not version controlled, not shared.
Fix: Move to project-level CLAUDE.md which is version controlled and automatically available to all developers who clone the repo.

Domain 3 — Practice Questions (10)

Q1. Test files are scattered throughout the codebase alongside their source files. You want uniform testing conventions. Best approach?
  • A) Add testing conventions to root CLAUDE.md — loads everywhere
  • B) Create .claude/rules/testing.md with paths: ["**/*.test.*"] — loads only for test files
  • C) Create a CLAUDE.md in every directory that contains test files
  • D) Create a skill that loads testing conventions on demand
B — Path-scoped rules in .claude/rules/ with glob patterns apply conventions by file type regardless of directory location. Root CLAUDE.md always loads (wastes tokens when not editing tests). Directory CLAUDE.md files can't cover scattered files. Skills require manual invocation.
Q2. A skill produces 3,000 tokens of verbose codebase analysis. You don't want this in your main conversation. Which frontmatter option isolates it?
  • A) output: suppress
  • B) context: fork
  • C) allowed-tools: none
  • D) mode: background
B — context: fork runs the skill in an isolated sub-agent context. Verbose output stays in the fork. Only the summary returns to the main conversation, keeping it clean.
Q3. You want a /security-audit command available to every developer without manual setup. Where does the file go?
  • A) ~/.claude/commands/security-audit.md
  • B) .claude/commands/security-audit.md
  • C) CLAUDE.md with a commands: section
  • D) .claude/skills/security-audit/SKILL.md
B — .claude/commands/ is version controlled and automatically available to all developers when they clone or pull the repo. ~/.claude/commands/ is personal only. CLAUDE.md cannot contain command definitions.
Q4. CI pipeline hangs on: claude "Review this PR for security issues". What is the fix?
  • A) Set CLAUDE_HEADLESS=true environment variable
  • B) Add the -p (--print) flag for non-interactive mode
  • C) Redirect stdin from /dev/null
  • D) Add the --batch flag
B — The -p (--print) flag runs Claude Code non-interactively. It processes the prompt, writes to stdout, and exits. Options A, C, D reference non-existent Claude Code features.
Q5. You run /memory in Claude Code. What does this command do?
  • A) Clears all conversation history to free context space
  • B) Shows which CLAUDE.md files are currently loaded in this session
  • C) Saves the current session to a named memory slot
  • D) Exports conversation history to a file
B — /memory shows which memory files (CLAUDE.md files) are currently loaded. Use it to diagnose why conventions aren't being applied — if a file isn't in the list, it's not being loaded.
Q6. When should you use --output-format json with --json-schema in CI?
  • A) When the review findings need to be posted as inline PR comments programmatically
  • B) When the model needs to think longer about complex code
  • C) When the codebase is too large for a single review pass
  • D) When multiple developers are reviewing simultaneously
A — --output-format json with --json-schema produces machine-parseable structured findings that your CI script can programmatically post as inline PR comments, create tickets, or route to other systems.
Q7. CLAUDE.md vs .claude/skills/ — when do you choose a skill over adding to CLAUDE.md?
  • A) When the convention is too complex for CLAUDE.md
  • B) When you need on-demand invocation for task-specific workflows rather than always-loaded universal standards
  • C) When the CLAUDE.md file exceeds 1,000 lines
  • D) When the skill needs to run faster than CLAUDE.md loading allows
B — CLAUDE.md is always loaded — use it for universal standards that apply to every session. Skills are on-demand — use them for specific workflows (codebase analysis, security audit) that you invoke intentionally, not every session.
Q8. A developer wants a personal variant of the team's code-review skill with stricter criteria, without affecting teammates. Where should they put it?
  • A) Override .claude/skills/review/SKILL.md with their version
  • B) Create a personal variant in ~/.claude/skills/ with a different name
  • C) Add their criteria to the project CLAUDE.md with their name as a comment
  • D) Fork the repository and modify the skill there
B — ~/.claude/skills/ is user-scoped and not version controlled. Creating a personal variant there with a different name (e.g., strict-review) avoids affecting the team's shared skill.
Q9. The @import syntax in CLAUDE.md is used for what purpose?
  • A) Importing code files for Claude to analyze
  • B) Referencing external files to keep CLAUDE.md modular and maintainable

client = anthropic.Anthropic()

extraction_tool = {
    "name": "extract_invoice_data",
    "description": "Extract structured invoice data from document text",
    "input_schema": {
        "type": "object",
        "properties": {
            "invoice_number": {"type": "string"},
            "vendor_name":    {"type": "string"},
            "total_amount":   {"type": "number"},
            "currency": {
                "type": "string",
                "enum": ["INR", "USD", "GBP", "EUR", "other"]
            },
            "payment_terms": {
                # nullable — returns null if not present in document
                # WITHOUT nullable, Claude fabricates a value
                "type": ["string", "null"],
                "description": "Null if not mentioned"
            },
            "calculated_total": {
                "type": "number",
                "description": "Sum of line items — used to catch semantic errors"
            }
        },
        "required": ["invoice_number", "vendor_name",
                     "total_amount", "currency", "calculated_total"]
    }
}

response = client.messages.create(
    model="claude-sonnet-4-20250514",
    max_tokens=1000,
    tools=[extraction_tool],
    tool_choice={"type": "tool", "name": "extract_invoice_data"},  # forced
    messages=[{"role": "user", "content": f"Extract: {document}"}]
)

# Read from tool_use block — NOT response.content[0].text
for block in response.content:
    if block.type == "tool_use":
        extracted = block.input  # your guaranteed JSON object

        # SEMANTIC VALIDATION — schema cannot catch this
        diff = abs(extracted["total_amount"] - extracted["calculated_total"])
        if diff > 1:
            print(f"Maths error: stated={extracted['total_amount']}, "
                  f"calculated={extracted['calculated_total']}")
⚠ Critical Distinction — Syntax vs Semantic Errors

tool_use + JSON schema eliminates: malformed JSON, wrong field types, missing required fields

Does NOT prevent: line items not summing to total, values in wrong fields, amounts misread from "forty five thousand"

Semantic validation is YOUR responsibility in code.

Q1. You set tool_choice: "auto" for your extraction tool. On some requests, Claude returns a text explanation instead of calling the tool. What is happening?
  • A) The tool description is too long
  • B) "auto" allows Claude to decide — it may return text; use "any" or forced selection to guarantee a tool call
  • C) The document exceeded the context window
  • D) The JSON schema has an error
B — tool_choice: "auto" is not a guarantee. Claude may decide a text response is more appropriate. For guaranteed structured output, use tool_choice: "any" (must call a tool) or {"type": "tool", "name": "..."} (must call this specific tool).
Q2. Your schema has vendor_address as required. 30% of invoices don't include an address. What will happen?
  • A) Extraction fails with a schema validation error
  • B) Claude returns null for the field
  • C) Claude fabricates an address to satisfy the required constraint
  • D) Claude asks the user to provide the missing address
C — Required fields that have no corresponding information in the source document cause Claude to fabricate values. Make such fields nullable (type: ["string", "null"]) so Claude returns null instead of invented data.
Q3. After adding few-shot examples, false positives drop from 40% to 15%, but unused-import warnings still have 80% false positive rate. What is correct next step?
  • A) Add more general examples to cover all patterns
  • B) Temporarily disable unused-import checking while adding specific examples for that pattern to restore developer trust
  • C) Switch to a larger model
  • D) Add a confidence threshold filter
B — High false positive rates in specific categories undermine developer trust in the whole system. Temporarily disable the problematic category while improving it with targeted examples. This is more effective than leaving it active with 80% false positive rate.
Q4. You submit 500 documents in a batch. 13 fail. How do you resubmit?
  • A) Resubmit all 500 with a modified prompt
  • B) Identify the 13 failed documents by their custom_id and resubmit only those with appropriate modifications
  • C) Increase max_tokens and resubmit all 500
  • D) Mark the 13 as exceptions and proceed without them
B — custom_id identifies each request-response pair. Resubmit only failed documents with appropriate modifications (e.g., chunking oversized documents). Resubmitting all 500 wastes cost and time.
Q5. Your invoice extraction keeps returning null for claim_date even when clearly stated. You've retried twice with no improvement. What should you do differently?
  • A) Make claim_date a required field to force extraction
  • B) Include the original document, the failed extraction, and the specific error ("claim_date stated as March 15 2024 but returned as null") in the retry prompt
  • C) Use a different model for date extraction
  • D) Split the document into smaller chunks
B — Generic retries without error feedback rarely succeed. The retry must include the original document, the failed extraction, AND the specific validation error. This gives Claude the context to identify and fix the specific extraction failure.
Q6. What does tool_use with JSON schema guarantee vs NOT guarantee?
  • A) Guarantees correct values; does not guarantee field names
  • B) Guarantees syntax (valid JSON, correct types, required fields present); does not prevent semantic errors (wrong totals, misplaced values)
  • C) Guarantees both syntax and semantics
  • D) Guarantees no hallucination; does not prevent format errors
B — JSON schema enforces structure (syntax). It cannot detect that line items don't sum to the stated total, or that an amount was placed in the wrong field — those are semantic errors requiring your validation code.
Q7. When is the Batch API NOT appropriate to use?
  • A) When processing more than 100 documents
  • B) For blocking workflows where users or developers wait for results
  • C) When documents vary in length
  • D) When extraction requires tool calling
B — The Batch API has no latency SLA and can take up to 24 hours. Never use it for blocking workflows (pre-merge checks, real-time user responses). Use it for latency-tolerant workloads: overnight reports, weekly audits, nightly test generation.
Q8. When should you use few-shot examples instead of detailed instructions?
  • A) Always — examples are always more effective than instructions
  • B) When detailed instructions alone produce inconsistent results and you need to demonstrate judgment for ambiguous cases
  • C) When the task involves code rather than natural language
  • D) Only when the model is unfamiliar with the domain
B — Few-shot examples are most effective when instructions produce inconsistent output, when you need to demonstrate ambiguous-case handling, or when you want the model to generalize judgment to novel patterns beyond pre-specified cases.
Q9. Which field design prevents Claude from fabricating values for optional information?
  • A) Setting a default value in the schema
  • B) Making the field nullable: type: ["string", "null"]

B — Nullable fields (type: ["string", "null"]) explicitly allow Claude to return null when the information isn't present. Required non-nullable fields cause fabrication. Empty string in description is just a prompt instruction — not schema enforcement.
Q10. The Batch API does not support which capability within a single request?

The Lost-in-the-Middle Effect

Claude has no persistent memory between API calls. Every call receives the full conversation history. Attention is highest at the beginning and end — information buried in the middle gets lower fidelity recall.

Glossary of Key Terms

stop_reason
Signal from Claude indicating why generation stopped. "tool_use" = wants to call a tool. "end_turn" = finished.
tool_use
When Claude decides to call a tool, it returns a response block of type "tool_use" with the tool name and parameters.
tool_result
The message you send back to Claude after executing a requested tool call. Contains the tool's output.
tool_choice
API parameter controlling whether Claude must call a tool ("any"), a specific tool ({type,name}), or may choose freely ("auto").
Agentic loop
The cycle: Claude reasons → requests tool → you execute → you return result → Claude reasons again. Repeats until end_turn.
MCP (Model Context Protocol)
Standard interface for connecting Claude to external tools and data sources. Defines how tools and resources are described and called.
Coordinator agent
The Claude instance that manages overall workflow — task decomposition, subagent delegation, result aggregation, error routing.
Subagent
A separate Claude instance spawned by a coordinator to handle a specific subtask. Has isolated context — no automatic inheritance.
Task tool
The mechanism in the Claude Agent SDK for a coordinator to spawn subagents. Must be in allowedTools.
PostToolUse hook
Intercepts tool results after execution but before Claude processes them. Used for data normalization and format standardization.
context: fork
SKILL.md frontmatter option that runs the skill in an isolated sub-agent context. Verbose output stays in the fork.
CLAUDE.md
Configuration file that Claude Code reads automatically. Contains project conventions, coding standards, and instructions.
Path-scoped rules
.claude/rules/ files with YAML frontmatter paths field containing glob patterns. Load only when editing matching files.
@import
CLAUDE.md syntax for referencing external files, keeping the main file modular and maintainable.
Plan mode
Claude Code mode where Claude explores and proposes an approach without making changes. For complex, multi-file, architectural tasks.
fork_session
Creates independent branches from a shared analysis baseline to explore divergent approaches simultaneously.
Lost in the middle
Phenomenon where LLMs have lower attention fidelity for information positioned in the middle of long inputs.

Structured block of critical transactional facts pinned in the system prompt at position 1 — never buried in conversation history.
isError flag
MCP tool response flag signaling failure to the agent. Enables structured error handling and recovery decisions.
isRetryable
Boolean in structured error responses indicating whether retrying the same request is appropriate.

Standard for describing the structure of JSON data. Used in tool input_schema to define what shape of data Claude should produce.
Semantic error
Logically incorrect data that passes schema validation — e.g., line items not summing to total. Requires custom validation code.
Nullable field
Schema field with type: ["string", "null"] allowing Claude to return null when information is absent rather than fabricating a value.
Few-shot prompting
Providing 2-4 concrete examples in the prompt to demonstrate desired output format and judgment for ambiguous cases.
Hub-and-spoke
Multi-agent architecture where a coordinator manages all inter-agent communication, routing, and error handling.
/compact
Claude Code command to reduce context usage during extended sessions when context fills with verbose discovery output.
